# CRISP-DM — Customer Intelligence & Segmentation Clustering

The six phases mapped to what this project actually does. Numbers come from the run
recorded in `artifacts/metrics.json` (seed 20260913).

---

## 1. Business understanding

**Question.** A retailer has two years of transactions and no customer segmentation.
Which groups exist, which ones carry the revenue, and what should be done with each?

**What makes an answer acceptable.** Two requirements were fixed before any modelling,
because both change what counts as the "best" model:

1. **Between 4 and 8 segments.** Fewer than four adds nothing over a 1–5 RFM quintile
   ranking, which is free. More than eight is more campaign tracks than a marketing
   team can staff.
2. **No segment below 3% of the base.** Below that it is an outlier pocket, not an
   audience.

**Why this is written down here.** These constraints are what produce a six-segment
answer — the validity indices on their own prefer k=2 and k=3 over anything in the
feasible band (see phase 5). Declaring the band
in advance is the difference between a stated business assumption and a post-hoc
rationalisation of a result that looked nice.

**Success criteria.** Segments that (a) survive resampling, (b) differ from the cheap
RFM-tier baseline, and (c) carry a plain-language action each.

---

## 2. Data understanding

**Source.** A transaction log shaped like UCI/Kaggle *Online Retail*: `InvoiceNo`,
`StockCode`, `Description`, `Quantity`, `InvoiceDate`, `UnitPrice`, `CustomerID`,
`Country`. Generated by `data/generate_data.py` under a fixed seed because the real
workbook is a ~45 MB authenticated download; see the README for that decision.

**Scale.** 60,221 lines, 1,277 customers, 11,080 invoices, 2009-12-11 → 2011-12-09.

**Defects present on purpose**, mirroring the real dataset:

| Defect | Volume | Why it matters |
|---|---|---|
| Guest checkout — `CustomerID` missing | ~3.5% of lines | Cannot be attributed to a customer; must be dropped, not imputed. |
| `C`-prefixed cancellation invoices | ~350 invoices | Real events with negative quantity — dropping them overstates loyalty. |
| Zero `UnitPrice` | ~0.4% of lines | Adjustments/samples, not revenue. |
| Exact duplicate lines | ~1% | Double-counts spend if left in. |

**Distribution shape.** Recency, frequency and monetary are all strongly right-skewed
— which is why `log_transform` is a searched dimension rather than a fixed choice.

## 3. Data preparation

`src/features.py`. Every drop is logged to `artifacts/cleaning_report.csv` and shown
in the dashboard, so the row count is auditable rather than asserted.

**Cleaning** (60,221 → 57,307 lines):

| Step | Lines removed |
|---|---|
| Exact duplicate lines | 596 |
| Missing `CustomerID` (guest checkout) | 2,086 |
| Non-cancellation rows with `Quantity ≤ 0` | 0 |
| Zero / negative `UnitPrice` | 232 |
| Cancellation lines | **kept** — negative revenue, and they feed `return_rate` |

**Aggregation** to one row per customer, at a fixed snapshot date (last invoice + 1
day) so recency is well defined:

- **RFM** (Hughes 1994) — `recency_days`, `frequency` (distinct purchase invoices),
  `monetary` (total spend).
- **Derived** — `avg_order_value`, `avg_basket_size`, `tenure_days`, `return_rate`,
  `distinct_products`.
- **Baseline** — 1–5 quintile scores `R_score` / `F_score` / `M_score` and their sum,
  used in phase 5 as the comparison the clustering has to beat.

Customers whose only activity is a refund (no positive spend) are excluded: 1,277 →
1,276.

Two feature sets go into the search — `rfm` (3 columns) and `rfm_extended` (7) —
because whether the derived behaviour features help is an empirical question, not one
to settle by assertion.

## 4. Modeling

`src/autoresearch.py`. A candidate is a **whole pipeline**, so preprocessing choices
compete on the same footing as the algorithm:

| Dimension | Values |
|---|---|
| feature set | `rfm`, `rfm_extended` |
| log1p transform | off, on |
| scaler | standard, robust, min-max |
| algorithm | k-means (k-means++), agglomerative (Ward), Gaussian mixture (EM) |
| k | 4 … 8 |

180 candidates.

**Search — steepest-ascent hill climbing with random restarts.** Evaluate every
neighbour one coordinate away (k moves by ±1; categoricals swap); move to the best
strictly-improving neighbour; stop when none improves. Six restarts, the first from a
fixed literature-standard start (`rfm`, log1p, standard, k-means, k=4) and the rest
random. Results are cached, so 80 distinct fits covered a 26-step search.

**Objective.**

```
J = 0.50 · (s + 1)/2  +  0.25 · 1/(1 + DB)  +  0.25 · CH/(CH + 500)
```

Silhouette carries the most weight because it is defined per-observation and is the
index this literature reports most; the other two break ties on compactness and
separation. Each term is bounded and monotone in its index's preferred direction, so
the blend can never reward a worse index.

**Constraint handling.** Infeasible candidates (k outside the band after a collapse,
or a segment under 3%) score `J − 1 − deficit` rather than `−∞`, so an infeasible
starting point still has a gradient back into the feasible region instead of trapping
the restart.

**Result.** `rfm`, no log transform, min-max, k-means, k=6.

## 5. Evaluation

`src/train.py`.

**Did the search work?** The full 180-configuration grid was run afterwards as a
verification pass the search never sees. Hill climbing reached the constrained global
optimum — **optimality gap 0.0000** — while skipping 100 fits. 161 of 180
configurations were feasible.

**Internal indices for the winner:** silhouette 0.541, Davies–Bouldin 0.637,
Calinski–Harabasz 2,259.7, composite 0.7427, smallest segment 6.7%.

**Stability.** Ten refits on 80% subsamples, compared with the full-data labels on the
shared customers: ARI **0.990 ± 0.008** (min 0.976). The solution is not an artefact
of these particular rows.

**Against the cheap baseline.** ARI **0.278** with the 1–5 RFM quintile tiers —
related, but not a restatement. The clustering is finding structure the axis-aligned
cuts do not.

**External sanity check.** The generator drew customers from six latent archetypes the
pipeline never sees: ARI **0.481**, NMI **0.660**. The crosstab
(`artifacts/archetype_crosstab.csv`) shows exactly where the disagreement is —
`champion` splits across Champions and Loyal Regulars, `hibernating` splits across
Hibernating and At Risk. Those archetypes genuinely overlap in RFM space, so this is
the expected result. It is a check that the output is not noise, not a benchmark
score.

**The finding worth reporting.** Scanning the best achievable composite at each k
below the feasible band (`artifacts/metrics.json` →
`search.unconstrained_reference`, recomputed on every training run) shows both k=2
and k=3 scoring *above* the k=6 winner:

| k | Best composite | Best pipeline | Smallest segment |
|---|---|---|---|
| 2 | 0.8035 | rfm_extended, robust, k-means | 10.9% |
| 3 | 0.7766 | rfm_extended, robust, agglomerative | 5.8% |
| 6 (winner) | 0.7427 | rfm, min-max, k-means | 6.7% |

Internal validity indices reward few well-separated blobs; they do not know what a
marketing team can use. The six-segment answer comes from the phase-1 constraint, not
from the objective. The elbow curve and the full-grid leaderboard ship in the
dashboard so this trade-off can be inspected rather than taken on trust.

**Weakest part of the solution.** Loyal Regulars, mean silhouette 0.394 — it sits
between Champions and Promising / New rather than in clean space of its own.

## 6. Deployment

`app.py` — a local Streamlit admin dashboard, six tabs:

| Tab | Contents |
|---|---|
| Overview | KPI tiles, customers and revenue share per segment, the full profile table with a recommended action per segment. |
| Segments | Per-segment drill-down: position in recency×spend space, profile against the base, member table with CSV export. |
| AutoResearch | Search trajectory (cumulative best + per-restart small multiples), optimality gap against the grid, the objective and constraint in full, k-diagnostics, the grid leaderboard. |
| Research grounding | Every index and algorithm against its original source, and how the implementation follows each. |
| Data & CRISP-DM | This phase map, the cleaning audit, the feature dictionary, feature distributions. |
| Model card | Selected pipeline, internal indices, the three validation checks, reproducibility block, a live scorer, and the limitations. |

**Scoring path.** `artifacts/best_pipeline.joblib` stores the fitted scaler plus the
cluster centroids in scaled space rather than the estimator, so a new customer is
assigned by nearest centroid. That works for every algorithm in the search space —
`AgglomerativeClustering` has no `predict` — and the dashboard shows the distance to
the runner-up segment so borderline customers are visible instead of hidden.

**Not in scope:** containerisation, authentication,
a served API, a scheduled retrain, or drift monitoring.

**Reproducibility.** One seed (20260913) drives data generation, the search, all model
fits and the stability trials. `python data/generate_data.py && python src/train.py`
reproduces every number in this document.
